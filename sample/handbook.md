## 1. RAG 综述与历史

RAG(Retrieval-Augmented Generation,检索增强生成)由 Meta AI 在 2020 年提出,核心思想是在生成阶段引入外部知识检索,缓解 LLM 的知识冻结与幻觉问题。RAG 的演进可分为三个阶段:朴素 RAG(检索 + 拼接 Prompt)、进阶 RAG(加入 Chunk 优化、Query 改写、重排序)、模块化 RAG(各环节可插拔、可组合)。

RAG 与微调(Fine-tuning)是知识更新的两种主要手段。微调是把新知识注入模型权重,适合模型能力本身的迁移;RAG 是把知识外置在向量库,适合需要引用来源、动态更新的场景。两者并非互斥,生产中常组合使用:RAG 处理时效性知识,微调处理领域表达风格。

## 2. RAG 核心流程

RAG 系统在数据准备阶段执行文档预处理(清洗、格式转换)、按 Chunking 策略切分(200-500 token 为常见粒度)、调用 Embedding 模型向量化、写入向量数据库(可选同步建 BM25 索引)。这一阶段离线执行,可批处理。

在线推理阶段,用户 Query 经 Query 改写后送入检索器,经 Dense 召回 + BM25 召回双路并行,RRF 融合得到候选集,再过 Cross-Encoder 精排取 Top-K。这些 Chunk 与原始 Query 拼成 Prompt 喂给 LLM,LLM 基于参考资料生成最终答案。整个流程可串行也可并行优化。

## 3. Chunking 策略

Chunking 策略直接决定检索粒度与上下文完整度。按 Markdown 标题切分能保留语义边界,适合结构化文档;按固定长度切分实现简单但易切断句子;Recursive Split 按段落/句子递归切分是常用折中。Chunk 过大导致召回不准,过小导致上下文断裂,200-500 token 是经验甜蜜点。

Parent-Child 索引是当前主流方案:父块保留完整上下文(如整个段落),子块用于精细召回(如每句话一个)。检索命中子块后扩展到父块,既保证召回粒度,又给 LLM 完整上下文。对于长文档(论文、法律条款),还可叠加大块摘要(512-1024 token)作为额外索引层。

## 4. Embedding 选型

Embedding 模型选型看三个维度:中文支持度、向量维度、检索 benchmark(MTEB 榜单)。中文场景常用 BGE-M3(1024 维,综合性能强)、BCE(百度,中文优化)、M3E(小模型,适合本地部署)。闭源可选 OpenAI text-embedding-3-large、阿里 DashScope 等。

关键约束:同一 RAG 系统内必须使用同一 Embedding 模型,否则向量空间不一致,检索全部失效。Embedding 模型对输入长度有限制(通常 512 token),超长文本需预先截断或切块。领域 Embedding 微调可提升 Recall 5-10%,但需数百条 Query-Chunk 配对标注,中小规模场景不划算。

## 5. 检索与重排

检索阶段通常采用 Dense + BM25 双路召回:Dense 擅长语义匹配,BM25 擅长关键词精确匹配,两者互补。RRF(Reciprocal Rank Fusion)是简单有效的融合方式,无需调权重,对量纲不敏感。生产中 Top-K 取 20-50,留足候选空间给重排序。

Cross-Encoder 重排序用 LLM 对 Query-Doc 对打分,精度显著高于双塔模型,但计算开销大(每对一次推理)。重排 Top-K 通常 5-10,直接喂给生成阶段。对于延迟敏感场景,可用蒸馏的小型 Cross-Encoder(如 BGE-Reranker)替代 LLM 重排,精度损失 < 5%,速度提升 10 倍以上。

## 6. 向量数据库选型

向量数据库的核心操作是 ANN(近似最近邻)搜索。主流索引结构:HNSW(基于图,召回率高、延迟低,首选)、IVF(倒排聚类,显存友好)、PQ(乘积量化,极致压缩)。HNSW 关键参数 M(每节点邻居数,16-48)、efConstruction(构建宽度,100-200),调优空间大。

选型上,Chroma 适合原型与 POC,Milvus/Qdrant 适合中大规模生产(支持分布式、亿级向量),PGVector 适合已有 Postgres 栈(运维简单,亿级以下)。向量库通常还提供元数据过滤(按文档、时间、标签),实现"语义相似 + 硬条件"的混合过滤,在企业场景非常关键。

## 7. Prompt 构造

RAG 场景的 Prompt 模板通常包含三段:角色定义(你是某领域助手)、参考资料(检索到的 Top-K Chunk,带编号)、用户问题(原始 Query)。参考资料前可加指令"基于以下参考资料回答,若参考资料不足请回答我不知道",有效降低幻觉率。

进阶技巧:Chain-of-Thought 让 LLM 先列推理步骤再给答案,适合复杂问题;Self-Consistency 多次采样取众数,适合需要稳定输出的场景;ReAct 把检索拆成多轮,适合多跳问题。注意 Prompt 中需明确"禁止编造参考资料中未提及的事实",否则 LLM 会用通用知识补全。

## 8. 效果评估

RAG 评估分两层:检索质量(Recall@K、MRR、NDCG)与生成质量(忠实度、相关性、流畅度)。检索评估需标注 Query-Chunk 配对,Recall@5 是最直接的信号——检索不到正确答案,后续生成再好也没用。生成评估可用 LLM-as-Judge(用 GPT-4 等强模型打分)或人工评估。

评估集构造有两条路径:从线上日志采样真实 Query 人工标注(贴近生产);用 GPT-4 根据文档生成合成 Query(成本低、可批量)。建议每天跑一次离线评估监控趋势变化,而非关注绝对数值。指标异常时优先排查:Embedding 是否变更、语料是否更新、Chunking 是否调整。

## 9. 性能与成本优化

性能优化点集中在三处:Embedding 批量调用(单次 API 调用批量传 100 条比单条循环快 5-10 倍)、检索 Top-K 调小(从 50 降到 20,精度损失通常 < 3%)、Prompt 压缩(参考资料去冗余、控制单 Chunk 长度)。生成侧 max_tokens 限制可避免 LLM 跑飞。

成本构成:Embedding API 调用(按 token 计费)+ LLM API 调用(按 token 计费)+ 向量库存储(按 GB/月)。高频 Query 的 Embedding 可缓存(命中率通常 30-60%),LLM 响应可缓存(命中率通常 10-20%)。生产环境建议配置成本看板,按日/按租户拆分,异常时告警。

## 10. 工程实践与坑点

常见坑 1:Chunking 不当导致上下文断裂。症状是 LLM 回答"我不知道"或答非所问。处理:检查 Chunk 边界是否切断主语/动词,尝试切换 Markdown 切分或调小 Chunk 长度。坑 2:Embedding 模型升级后未重建索引。症状是新语料召回不到,但人工看 Chunk 明明相关。处理:索引重建期间双写,平滑切换。

坑 3:Prompt 没约束导致 LLM 自由发挥。症状是 LLM 引用了参考资料外的内容,胡编乱造。处理:Prompt 加硬约束"只使用参考资料中的信息"。坑 4:Top-K 过大导致上下文超限。症状是 LLM 回答截断或丢失中间内容。处理:控制单 Chunk 长度 + 控制 Chunk 数量,确保总长度 < 模型上下文的 50%。
